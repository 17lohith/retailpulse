## 2. Data strategy — the "fine-tuned" dataset (answers: no public expiry/waste data exists)

### 2.1 Real data we have (downloaded and verified 2026-10-23)
| Dataset | Location | Verified facts |
|---|---|---|
| Amazon Reviews 2023 — Grocery reviews | `data/raw/amazon2023/Grocery_and_Gourmet_Food.jsonl` | 5,973,991,903 bytes (matches server); 14.3M reviews per dataset card; fields rating, title, text, asin, parent_asin, user_id, timestamp(ms), helpful_vote, verified_purchase |
| Amazon Reviews 2023 — Grocery metadata | `.../meta_Grocery_and_Gourmet_Food.jsonl` | 1.38 GB; **603,274 products**; `store`(brand) present 97.1%; **price present only 37.2%** (and sometimes stored as a string → cleaning needed); categories depth ≥ 3 for 85.4%; nested `details` dict varies per product |

| Store Sales (Kaggle, Favorita) | `data/raw/store_sales/` | **train.csv 3,000,888 rows**, 54 stores, 33 families, daily 2013-01-01 → 2017-08-15; + stores, oil, holidays_events, transactions. Kaggle token verified working |

### 2.2 Three data layers (never mixed up in the report)
| Layer | Source | Truth status | Used for |
|---|---|---|---|
| **L1 Reviews analytics** | Amazon reviews + metadata | REAL | Big Data MapReduce; "customer feedback/product insight" screens |
| **L2 Demand** | Store Sales | REAL (store × product-family level) | Forecast training/evaluation (honest metrics), Hadoop sales jobs, cloud BQML |
| **L3 Operations "RetailPulse Demo Retail"** | Generated by us | **SIMULATED — every record carries `simulated:true`** | SKU-level sales, stock, batches, expiry, suppliers, purchase orders, waste — the data the management system needs and no one publishes |

### 2.3 How L3 is generated (deterministic, seeded, documented, reproducible)
1. **Catalog:** sample ~1,500 real products from Amazon metadata (names, brand, category, price where present; otherwise price sampled from that category's observed price distribution, flagged `price_imputed:true`). Map Amazon categories → Favorita families with a documented table (e.g., Beverages→BEVERAGES, Snack Foods→GROCERY I, Dairy→DAIRY…); families with no Amazon analogue (PRODUCE, MEATS, BREAD/BAKERY, POULTRY, SEAFOOD, EGGS, DELI) get template products flagged `catalog_source:"template"`.
2. **Demand:** take the **real** family × store daily sales from Favorita for 3 demo stores, and split each family's daily total across its SKUs with a long-tail (Zipf-like) share plus Poisson noise, keeping family totals equal to real sales. SKU-level numbers are therefore *derived*, not observed; no SKU-level accuracy claim is ever made — accuracy is reported at the real family level only.
3. **Shelf life:** per-category table (e.g., bakery 3 d, dairy 10 d, produce 5 d, packaged dry 270 d …). These are **our assumptions**, listed in the report as assumptions with a note that real values vary by product.
4. **Supply side:** suppliers, lead times (2–7 d), pack sizes, min order quantities; a simple (s,S) reorder policy run forward in time creates purchase orders, **batches with expiry**, stock-outs, and expired/wasted units — realistic dynamics, but simulated.
5. **Chain structure:** Demo A = single-owner store (1 store); Demo B = 3-store small chain; (Demo C optional 5-store). Multi-tenant: each is a separate `tenantId`.
6. **Size:** ~3 stores × ~1,500 SKUs × 2 years daily ≈ 3M sales lines — fits Hadoop + Mongo comfortably.
7. Scripts + seed + a `DATA_CARD.md` describing every assumption go in `retailpulse/simulation/`.

> Rule for the report/paper: results on L2 are "real-data" results; anything on L3 is "simulation-based demonstration of workflow", never presented as evidence of real savings.

## 5. Big Data module (23DC2044)
**Hadoop jobs (Hadoop Streaming, Python mapper/reducer, combiners where valid):**
| # | Input | Job | Output |
|---|---|---|---|
| J1 | reviews | token frequency by rating bucket (stop-words documented) | top terms per 1–5★ |
| J2 | reviews | per-product count, mean rating, star histogram | product stats |
| J3 | reviews | review volume by month/year | time series |
| J4 | reviews + meta | **reduce-side join** on `parent_asin` → price band × rating, category × rating | insight tables |
| J5 | meta (+J2) | brand (`store`) ranking by review count and mean rating | brand table |
| J6 | reviews | verified vs unverified; helpful-vote distribution | stats |
| J7 | Store Sales | sales by family × month | demand seasonality |
| J8 | Store Sales | promo vs non-promo mean sales by family | promo lift |
| J9 | Store Sales | store × weekday profile | forecasting features |
| J10 | simulated ops | waste/expiry units by category and store | waste report |
**Validation:** each job compared with pandas (and Mongo `$group` where size allows) on a sample and on the full set where feasible; differences logged.
**Cleaning log:** malformed JSON lines, price strings, null brands, timestamp ms→date, duplicates — before/after counts recorded.
**MongoDB integration:** bulk-insert full product metadata (603K), a stratified review sample (default 2M; full 14.3M optional — see Decision R-3), L3 data, and all `mr_results`; demo insert/query/update/delete + indexes + explain().
**Engineering:** 6 GB input on one node → set split size, run mappers in parallel (12 cores, YARN 6 GB), record wall-clock times per job (report table).

## 6. Forecasting & decision logic (shared by all three subjects)
- **Data:** L2 real family-level daily series (train ≤ 2017-07-18, **hold-out last 28 days**).
- **Models:** naive, seasonal-naive(7), 7-day moving average, ETS/Holt-Winters, SARIMAX with promo + holiday regressors, gradient-boosting (lag/weekday/promo/oil features). Metrics: MAE, RMSE, sMAPE, MASE; model selection per family; **report even if the baseline wins**.
- **Cloud comparison:** same split in BigQuery ML ARIMA_PLUS(_XREG) → compare with local results (teammate runs).
- **Reorder rule (transparent):** `need = forecast(lead_time + review_period) + safety_stock − on_hand − on_order`, rounded up to pack size / MOQ; safety stock = z·σ_forecast_error·√(lead time); every recommendation stores inputs + a plain-language reason.
- **Expiry risk:** for each batch: `expected_sales_before_expiry` vs `qty_remaining` → flag, suggest rotate / pause reorder / markdown.
- **Classification:** fast / stable / slow / non-moving by sales velocity and days-of-cover.
